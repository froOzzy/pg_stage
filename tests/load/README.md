# Нагрузочные тесты

Тесты измеряют обработку plain-дампа через `PlainObfuscator.run` на Linux.
Обычный `pytest` пропускает их. Дополнительные зависимости не нужны.

В GitHub Actions отдельный job `Load tests` в workflow `PyTest` запускается
после успешного job обычных тестов при каждом push. Он использует Ubuntu 24.04
и Python 3.11, обрабатывает по 100 000 строк в трёх повторениях для обоих режимов
вывода. JSON-отчёт и JUnit XML сохраняются в артефакте `load-test-reports`
на 14 дней, в том числе после падения тестов, если отчёты успели сформироваться.
CI задаёт консервативные границы: не менее 2000 строк/с, не более 256 MiB RSS
и 128 MiB физических записей за повтор. Они ловят грубые регрессии; для сравнения
малых изменений скорости нужны сопоставимые машины и отдельный baseline.

Из корня проекта:

```bash
nix-shell
python -m pytest tests/load --run-load -q
```

По умолчанию запускаются 7 сценариев, каждый в двух режимах вывода,
по 100 000 строк на таблицу и 3 повторения. Каждый замер выполняется
в новом процессе последовательно, без конкуренции между тестами.
Результаты сохраняются в `load-results.json`, который исключён из Git.

## Сценарии

| Сценарий | Нагрузка |
| --- | --- |
| `passthrough` | Таблица без правил обфускации |
| `mutation` | Одна простая мутация в строке из 6 колонок |
| `wide` | Одна мутация в строке из 100 колонок |
| `conditions` | Условная мутация для половины строк |
| `source_column` | UUID на основе обфусцированной колонки |
| `relations` | Две таблицы с одинаковыми ключами, генерация и повторное использование соответствий |
| `json` | Обфускация ключей на двух уровнях JSON |

В `relations` обрабатывается вдвое больше строк, чем задано `--load-rows`.
Рост памяти этого сценария ожидаем: проект сохраняет соответствия ключей.
Целостность связей проверяется сравнением SHA-256 всех строк двух таблиц.
Во всех сценариях проверяется число выходных строк, а содержимое и порядок
колонок проверяются попарно через каждые 1000 строк каждой таблицы: индексы
0/1, 1000/1001 и далее. Так выборка включает обе ветки условия. Быстрый тест
валидатора отдельно отвергает ошибочную мутацию строки с ложным условием.

Дополнительно два теста роста памяти (`wide` и `json`) сравнивают свежие процессы
с 2000 и 50000 строк: увеличение пикового RSS допускается не более чем на 24 MiB.
Relations исключён из этой проверки, поскольку его кэш закономерно растёт.
Эти проверки выполняются с `--run-load` независимо от `--load-rows` и режима вывода;
их замеры сохраняются с `measurement=memory_scaling`, отдельно от сводок скорости.

## Метрики

- Время обработки, строки/секунду и входные МиБ/секунду.
- CPU user/system и процент загрузки относительно одного ядра.
- RSS до и после обработки, пиковая RSS процесса из `/proc/self/status` (`VmHWM`).
- Дисковые `read_bytes`/`write_bytes`, логические `rchar`/`wchar` и число
  системных вызовов чтения/записи из `/proc/self/io`.
- Блочный I/O, minor/major page faults, переключения контекста из `getrusage`.
- Размер входа/выхода, отдельные повторения, медианы скорости и максимумы памяти/I/O.
- Версия Python, ОС, Git-коммит, наличие незакоммиченных изменений и параметры запуска.

Замер времени включает потоковую генерацию входа, обфускацию, подсчёт размера
выхода и проверки результата. Импорт модулей и создание обфускатора происходят
до замера времени, но входят в пиковую RSS процесса. RSS берётся из `/proc`,
поскольку `ru_maxrss` может отражать унаследованный максимум родительского процесса.
Дамп и результат не накапливаются целиком в памяти.

`discard` отбрасывает результат после подсчёта байтов и проверки; тест требует
отсутствия дисковых записей. `file` пишет результат во временный файл,
включая `flush` и `fsync` в замер времени, и автоматически удаляет файл после замера.
Каталог можно выбрать через `--load-tmp-dir`, например на том же разделе, где
хранятся рабочие дампы. По умолчанию используется системный временный каталог.
На tmpfs физические записи могут быть нулевыми даже в режиме `file`.

Это счётчики I/O конкретного процесса, а не процент занятости диска или точная
нагрузка на физический накопитель. Файловый кэш и файловая система влияют на
результат. Чтение `/proc` добавляет небольшой объём к логическим счётчикам чтения.
Вход генерируется в памяти, поэтому чтение реального файла дампа здесь не измеряется.
Скорость PostgreSQL, `pg_dump`, восстановления и custom-формат эти тесты не измеряют.

## Управление нагрузкой и порогами

Короткая проверка всех сценариев:

```bash
python -m pytest tests/load --run-load --load-rows 2000 --load-repeats 1 -q
```

Большая связанная таблица без записи результата на диск:

```bash
python -m pytest tests/load --run-load -k relations \
  --load-rows 1000000 --load-repeats 3 --load-output-mode discard \
  --load-timeout 300 --load-report load-results-relations.json -q
```

Проверка заданных ограничений на отдельном сценарии:

```bash
python -m pytest tests/load --run-load -k mutation \
  --load-output-mode discard \
  --load-min-rows-per-second 50000 --load-max-rss-mib 128 \
  --load-max-write-mib 0 -q
```

Числа в последнем примере иллюстративные: сначала соберите базовые показатели
на своей машине. Без указанных порогов тесты измеряют ресурсы и проверяют
корректность; универсального ограничения скорости или памяти нет.
Порог скорости применяется к медиане повторений, пороги RSS и дисковых записей —
к максимуму. При нарушении порога тест падает, а измерения сохраняются в отчёте.
Ошибки и таймауты worker также записываются с контекстом сценария и stderr;
отсутствие Git-репозитория не мешает сохранить отчёт (commit/dirty будут null).
Зависший процесс ограничен `--load-timeout` (120 секунд по умолчанию на повторение).

Для сравнения изменений запускайте одинаковые команды на одинаковом оборудовании
при сопоставимой фоновой нагрузке. Чтобы увидеть рост памяти с объёмом данных,
повторите сценарий с несколькими значениями `--load-rows` и разными путями отчёта.
Абсолютные значения из коротких запусков особенно чувствительны к шуму и кэшу ОС.
